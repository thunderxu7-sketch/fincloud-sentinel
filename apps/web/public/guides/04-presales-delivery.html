04 / PRESALES & SOLUTION DELIVERY

售前不是讲产品，而是降低客户做决定的风险。

01 / 先用生活例子理解

把售前想成请建筑师设计一座医院。

客户说“我要一栋先进的大楼”不是完整需求。建筑师必须先问服务多少人、哪些科室、停电能撑多久、预算和工期，再比较方案、做样板间、算总成本并制定施工计划。

生活类比

不是卖最贵的材料，而是证明这栋楼能用

如果不知道病床数和应急等级，就无法判断电梯、供电和消防怎么选。方案的价值不是产品列表多，而是每个选择都能回到业务目标、约束与可验证结果。

问科室和人流→

需求调研：业务目标、用户旅程、现状痛点和利益相关者。

确定结构与材料→

方案选型：按容量、安全、合规、运维和成本比较候选能力。

先做样板间→

POC：用最小范围验证最大不确定性，不是做一个缩小版生产。

正式招标答疑→

RFP：逐条回应要求，标明满足、偏差、假设和证据。

预算和施工计划→

TCO/ROI 与交付：算全生命周期成本并明确阶段、责任和退出条件。

02 / 六个核心能力

把技术讨论变成客户可以批准的决策。

01

需求调研 Discovery

不仅问“想用什么产品”，还要问业务结果、现状基线、交易量、峰值、数据分类、合规、恢复目标、团队能力和决策流程。

outcome + baseline + constraint
+ stakeholder + decision date
02

方案选型 Selection

建立需求到能力的追踪矩阵，比较性能、安全、可用性、生态、锁定风险、运维复杂度与成本，并记录为什么不选其他方案。

requirement → capability
→ option → trade-off → decision
03

POC 验证

围绕最关键风险设计可复现测试，提前约定数据集、负载、成功阈值、证据格式、负责人和失败后的决策。

hypothesis + metric + threshold
+ owner + evidence + exit
04

RFP 应答

逐项说明 Fully / Partially / Not supported，附架构、控制、限制和证明材料。对未知项写假设，不用模糊措辞掩盖缺口。

requirement ID → response
→ evidence → deviation → owner
05

TCO / ROI

TCO 计算云资源、软件、网络、迁移、人力、支持和风险成本；ROI 用节省成本、减少损失、提升收入或缩短上市时间衡量收益。

ROI = (benefit - total cost) / total cost
show assumptions and sensitivity
06

交付规划

把方案拆成发现、基础环境、迁移、验证、灰度和运营阶段，明确 RACI、依赖、风险、回滚、培训、验收与交接。

phase → deliverable → gate
→ owner → risk → rollback
03 / 一次售前项目如何推进

每一阶段都要产生决策，而不只是文档。

STEP 01

发现与资格判断

确认业务痛点、预算、决策人、时间窗口和是否值得双方继续投入。

STEP 02

基线与需求矩阵

量化容量、SLO、RPO/RTO、安全、数据驻留和现有成本，排出优先级。

STEP 03

方案与取舍

给出高阶架构、产品映射、备选方案、风险和责任边界，并获得客户确认。

STEP 04

POC 与商业论证

按计分卡收集证据，同时建立 TCO/ROI 和实施估算，形成 go / no-go 建议。

STEP 05

路线图与交接

把承诺转成里程碑、RACI、验收门禁、运营模型和风险清单，避免售前结束后信息丢失。

04 / 每份材料回答什么问题

文档不是产出目的，决策才是。

材料回答的问题必须包含完成标准
Discovery 记录客户为什么现在要做？目标、基线、约束、决策人、时间关键假设已被客户确认
需求与 NFR什么叫“满足要求”？容量、SLO、安全、合规、RPO/RTO每项有优先级和验收方式
高阶方案为什么这样选？架构、产品映射、数据流、取舍、边界需求可追踪到架构控制
POC 计分卡最大风险被证明了吗？用例、数据、阈值、证据、owner、退出条件双方签署结果与下一步
RFP 应答供应商是否满足正式要求？逐条状态、证据、偏差、假设不存在无 owner 的缺口
TCO / ROI这个决定经济上合理吗？成本口径、收益假设、敏感性和时间范围财务与业务共同认可口径
交付计划谁在什么时候怎么上线？阶段、RACI、风险、回滚、培训、验收售前承诺已进入交付基线

90 秒口述版本。

“我理解售前的核心不是介绍产品，而是降低客户决策风险。我通常先做需求调研，确认业务目标、现状基线、非功能指标和决策流程；再建立需求到能力的追踪矩阵，对不同方案做取舍；对于最大不确定性，用双方预先同意的指标和证据做 POC；进入正式采购时，用 RFP 逐项说明满足程度和偏差；同时建立 TCO/ROI，明确成本与收益假设；最后把承诺转成交付阶段、RACI、风险、回滚和验收门禁。FinCloud Sentinel 仓库里包含这一整套材料，并且 POC 指标能对应到真实代码和在线演示。”
表达结构

使用“发现—设计—证明—决策—交付”五段式。每一段都说清输入、产出和客户决策。

07 / 面试官继续追问

四个高频问题。

客户一开始就指定某个产品怎么办？

先尊重方向，再追问产品背后的目标和约束，确认它是强制标准、偏好还是尚未验证的假设。随后用需求追踪矩阵验证是否合适，并透明说明替代方案和迁移成本。

POC 怎么避免变成无限期免费开发？

在开始前锁定假设、范围、数据、时间、负责人、成功阈值和退出决策。新增需求进入变更清单，不直接扩进当前 POC；POC 只验证最大风险，不承担全部生产功能。

TCO/ROI 数字不确定怎么办？

不要制造精确幻觉。把已知、假设和范围分别标注，提供基准/乐观/保守三种情景和敏感性分析，并让业务、财务、技术共同确认口径。

售前如何顺利交接给交付团队？

把需求基线、架构决策、POC 证据、承诺、偏差、风险、RACI 和验收门禁放进同一交接包，安排联合评审，并确保未决事项都有 owner 和日期。

08 / 不要这样说

四个常见售前误区。

!

“客户要什么我就配什么”

解决方案师必须验证目标和约束，而不是把产品需求原样转成报价单。

!

“POC 跑通就证明能上生产”

POC 只证明约定假设，生产还需容量、安全、合规、运营与迁移验证。

!

“ROI 一定很高”

没有公开假设、时间范围和敏感性分析的 ROI 不可信。

!

“签约后交给实施就行”

售前承诺若未进入交付基线，会形成范围、成本和信任风险。

学完后的自检

尝试用一个真实岗位场景完成右侧四项，而不是只背流程名称。
