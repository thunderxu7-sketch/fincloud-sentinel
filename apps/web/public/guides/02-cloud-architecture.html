01 / 先用生活例子理解

把一个小餐馆扩成全国连锁。

配方一致只是第一步，还要决定门店选址、开多少灶台、如何升级菜单、如何统一建设门店，以及停电或城市封控时怎么继续营业。

生活类比

标准餐盒 + 连锁运营系统

Docker 像把配方和厨具装进标准餐盒；Kubernetes 像区域运营中心；Helm 是门店开业手册的版本；Terraform 是门店、水电和仓库的施工图；监控是经营看板；灾备是备用中央厨房。

标准餐盒→

容器镜像把程序、依赖与启动方式封装为一致制品。

区域运营中心→

Kubernetes 根据期望状态调度副本、重启故障实例并滚动发布。

开店版本手册→

Helm 把 Deployment、Service、配置和安全策略打包并参数化。

施工图纸→

Terraform 声明网络、集群、数据库等资源，让环境可审查、可重复。

备用中央厨房→

灾备用明确的 RPO/RTO、切换门禁和演练证明恢复能力。

02 / 六个核心能力

每个工具只解决一类问题。

面试时先说职责边界，再说产品；否则很容易变成没有设计依据的“技术全家桶”。

01

容器化 Containerization

镜像是不可变交付物，开发、测试、生产运行同一个 SHA。多阶段构建、非 root 用户和最小基础镜像降低体积与攻击面。

source → image digest
same artifact across environments
02

Kubernetes

用 Deployment 描述副本和升级策略，用 Service 暴露网络，用探针判断健康，用资源限制避免单服务拖垮节点。

desired state → scheduler → pods
readiness ≠ liveness
03

Helm

把一组 Kubernetes 清单做成版本化 Chart。不同环境只替换 values，而不是复制三套容易漂移的 YAML。

chart + values-prod.yaml
→ repeatable release
04

Terraform

把 VPC、子网、ACK、负载均衡和托管服务写成声明式代码，通过 plan 先看差异，再经过审批 apply。

code → plan → review → apply
state must be protected
05

监控与可观测性

指标告诉你“是否坏了”，日志解释“发生了什么”，链路说明“坏在哪里”。最终用 SLO 和错误预算决定告警与发布节奏。

metrics + logs + traces
→ SLO → alert → runbook
06

灾备 DR

RPO 是最多能丢多少数据，RTO 是多久恢复。真正的灾备包含数据复制、写入隔离、切换步骤、对账门禁和定期演练。

fence old writer → promote
→ reconcile → reopen traffic
03 / 一次生产发布如何完成

基础设施和应用分开变更，但共享验收门禁。

STEP 01

构建不可变镜像

测试通过后生成带提交 SHA 的镜像，扫描依赖和镜像漏洞，不在服务器现场编译。

STEP 02

规划云资源差异

Terraform plan 展示将新增、修改、销毁的资源，高风险差异需要人工审批。

STEP 03

Helm 渐进发布

使用同一 Chart 和环境 values，配置探针、资源限制、PodDisruptionBudget 与滚动策略。

STEP 04

SLO 守门

观察错误率、P95/P99 时延、饱和度和业务完整性指标，超过预算就自动停止或回滚。

STEP 05

恢复能力验证

故障注入或演练验证副本自愈、服务降级、数据恢复和对账完成后再宣布成功。

04 / 工具职责边界

知道“它不负责什么”，比会写命令更重要。

能力主要负责不直接负责验收证据
Docker可重复的程序运行包跨节点调度、灾备与业务一致性镜像摘要、SBOM、扫描结果
Kubernetes调度、自愈、服务发现、滚动升级自动保证数据库和资金正确探针、资源策略、发布状态
Helm应用清单模板化与版本管理创建 VPC、ACK、数据库实例lint、template、release version
Terraform云资源生命周期与变更计划应用内部业务流程fmt、validate、plan、审批记录
Prometheus / ARMS指标、告警、SLO与趋势替代日志、链路和事故流程规则、dashboard、runbook 链接
多可用区 / DR降低单点故障并恢复业务自动证明切换后账务一致RPO/RTO、演练时间线、对账报告

06 / 面试可以直接这样讲

90 秒口述版本。

“我不会把云架构简单理解为上 Kubernetes，而是分六层。容器保证制品一致；Kubernetes负责调度、自愈和渐进发布；Helm管理应用清单版本；Terraform让网络、集群和托管服务可重复创建；可观测性用指标、日志、链路和 SLO 发现问题；灾备用明确 RPO/RTO、写入隔离、切换和对账证明恢复。我的项目提供 Pages、Docker 和阿里云生产映射三层环境，能展示镜像构建、Helm/Terraform 验证、Prometheus/Grafana 以及回滚和灾备 Runbook。”
表达结构

先讲每层解决的问题，再说部署层次和证据。不要说“用了 Kubernetes 所以高可用”。

07 / 面试官继续追问

四个高频问题。

Docker Compose 和 Kubernetes 的分界在哪里？

Compose 适合本地集成和单机演示；Kubernetes 适合多节点调度、自愈、渐进发布、隔离和平台治理。是否上 K8s 取决于团队规模、可用性、发布频率和运维能力，不是项目越大越必须。

Helm 和 Terraform 为什么不能只选一个？

Terraform 更适合管理云资源及其生命周期；Helm 更适合管理 Kubernetes 内的应用发布。可以由 Terraform 安装 Helm release，但仍应保持基础设施与应用版本的责任边界。

多可用区就等于灾备吗？

不是。多可用区主要处理区域内故障；灾备还需要跨故障域的数据策略、RPO/RTO、写入隔离、流量切换、依赖验证和业务对账，并通过演练证明。

监控很多指标为什么还是会漏告警？

因为指标数量不等于可运营性。应从用户结果定义 SLI/SLO，使用多窗口燃烧率告警减少噪声，并为每条告警指定 owner、dashboard 和 runbook。

08 / 不要这样说

四个常见架构误区。

!

“上云以后天然高可用”

云只提供能力，副本、故障域、数据策略和恢复流程仍需设计验证。

!

“Pod 重启就是自愈”

实例恢复不代表业务恢复；还要检查依赖、积压、账务和客户影响。

!

“Terraform 可以随时重建生产”

状态、数据、密钥和外部依赖不能只靠 IaC 重建，必须有备份与恢复设计。

!

“有 Grafana 就算可观测”

真正的可观测性还包括高质量遥测、SLO、告警路由和可执行手册。

学完后的自检

不背产品清单，先证明自己能解释职责边界和故障恢复。
