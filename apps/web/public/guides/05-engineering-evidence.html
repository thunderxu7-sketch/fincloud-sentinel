05 / ENGINEERING EVIDENCE

工程能力，不是“我会”，而是“我能证明”。

测试证明关键规则可回归，CI 保证每次变更重复执行，CodeQL 和 Trivy 检查安全风险，公开代码让设计可审查，在线演示证明结果真的能够运行。

一句话先懂成熟工程不是让代码“在我电脑上能跑”，而是把正确性、安全性、可构建性和线上行为变成任何人都能重复检查的证据。
01 / 先用生活例子理解

把软件交付想成一架飞机起飞。

飞行员经验丰富很重要，但航空安全不能只依赖“相信他”。飞机需要检查单、双人复核、黑匣子、维护记录和每次起飞前重复执行的门禁。

生活类比

能力要固化成流程和记录

单元测试像检查一个仪表；端到端测试像完整滑行；CI 是每次起飞都自动执行检查单；安全扫描检查已知和潜在结构风险；公开代码与在线演示像适航证和试飞记录。

部件检测→

单元测试验证金额、状态机、风险和账本等小范围规则。

整机滑行→

集成与 E2E 测试验证多个组件组合后的真实用户路径。

起飞检查单→

CI 在干净环境中重复安装、检查、构建、扫描和发布。

结构与材料检查→

CodeQL、Trivy、Gitleaks 检查代码、依赖、镜像、IaC 和秘密。

适航与试飞记录→

公开仓库、Actions 结果与在线演示让第三方独立验证。

02 / 五类工程证据

每类证据回答一个不同问题。

01

测试 Tests

单元测试验证纯规则，API 测试验证契约，AI 评测验证知识和策略，E2E 验证用户真实路径。重点覆盖资金不变量和故障分支。

fast rules → service contract
→ browser control loop
02

持续集成 CI

每次 push 和 PR 都从干净环境安装依赖，执行 lint、类型、测试、文档、API 契约、构建与安全检查，失败就阻止合并。

change → reproducible gates
green commit ≠ local promise
03

CodeQL

把代码转换为可查询的语义数据库，沿数据流寻找注入、不安全调用等模式。它比简单文本搜索更理解变量如何传播。

source → semantic database
→ security queries → finding
04

Trivy 与供应链扫描

检查依赖和镜像中的已知 CVE，也扫描文件系统和 IaC 配置。结合严重级别、可修复性和实际暴露面决定门禁。

dependencies + image + IaC
→ CVE / misconfiguration
05

公开代码 Public Code

仓库展示真实提交历史、架构决策、测试、CI 和安全策略。评审者可以验证实现是否与简历描述一致。

claim → source → test → workflow
traceable engineering evidence
06

在线演示 Live Demo

在线页面证明构建和部署成立，交互流程证明不是静态截图。配合边界说明，既有可用性又不冒充生产系统。

deployed SHA → public URL
→ observable user workflow
03 / 一次提交如何变成可信版本

只有全部门禁通过，提交才获得“可交付”资格。

STEP 01

静态与快速检查

lint、类型检查、格式和 API 契约尽快反馈明显错误。

STEP 02

规则与服务测试

运行领域、API、Python 及 AI 评测，验证关键不变量和安全策略。

STEP 03

浏览器 E2E

在真实 Chromium 中完成交易闭环、双语移动端和独立页面导航。

STEP 04

安全与制品验证

CodeQL、Trivy、Gitleaks、Helm/Terraform 校验和三个容器镜像构建并行执行。

STEP 05

部署与线上复核

发布 GitHub Pages 后，再运行线上操作链路，确认资产、路由和交互没有部署差异。

04 / 测什么、为什么测

测试数量不是目标，风险覆盖才是。

层级主要风险典型用例失败时说明
领域单元测试资金和状态规则错误金额精度、非法跳转、借贷平衡、对账问题码核心业务不变量被破坏
API 测试接口契约或组合逻辑错误创建交易、幂等重放、风险响应、指标服务边界与领域层不一致
AI 评测召回错误、证据缺失或越权动作预期 Runbook、非空引用、审批策略模型/知识/策略不能安全发布
浏览器 E2E组件组合、事件或路由失效审核—结算—对账—调查—隔离用户实际工作流不可用

部署验证构建成功但线上资源或路径错误Pages 子路径、容器镜像、在线实操交付制品与本地行为不一致
05 / FINCLOUD SENTINEL 中如何落地

工程主张全部能沿仓库追溯。

项目当前将功能正确性、安全、平台配置、容器制品和公开部署纳入同一套自动化门禁。

TESTS

20 个代码级检查

9 个领域、4 个 API、4 个 Web、3 个 Python 测试覆盖核心实现。

E2E

4 条浏览器流程

完整控制闭环、英文移动端交易、独立页面导航与五篇讲解发布。

AI EVAL

4/4 评测门禁

预期知识命中、证据存在且高风险动作必须审批。

SECURITY

CodeQL + Trivy + Gitleaks

语义代码分析、依赖/文件系统/IaC 扫描以及秘密检测。

PLATFORM

Helm / Terraform / Compose

Chart lint/template、Terraform fmt/init/validate 与 Compose 配置校验。

DELIVERY

镜像与 Pages

Web、Core API、AI Copilot 镜像构建，Pages 自动部署并执行线上复核。

证据口径自动化通过只证明当前用例和规则覆盖的范围，不等于“零缺陷”或生产认证。生产交付还需要真实负载、安全评审、渗透测试、变更治理和持续运营数据。
06 / 面试可以直接这样讲

90 秒口述版本。

“我会把工程能力转成五类可验证证据。第一是测试，用单元、API、AI 评测和 E2E 分层覆盖资金规则与用户流程；第二是 CI，让每次提交在干净环境重复执行检查；第三是安全扫描，CodeQL 查语义代码风险，Trivy 查依赖、镜像和 IaC，Gitleaks 防秘密进入仓库；第四是公开代码，让架构决策、测试和提交历史可审查；第五是在线演示，证明构建、部署和真实交互成立。FinCloud Sentinel 当前有 20 个代码级测试、4 条浏览器流程、4/4 AI 评测，并在 CI 中构建三个镜像、校验平台配置和自动部署 Pages。”
表达结构

不要只报测试数量；要说每个门禁防什么风险，以及第三方在哪里看到证据。

07 / 面试官继续追问

四个高频问题。

单元测试很多，为什么还需要 E2E？

单元测试快、定位准，适合业务不变量；但它无法证明浏览器事件、组件组合、静态路由和下载等真实用户路径。E2E 数量应少而关键，覆盖最有价值的闭环。

CodeQL 和 Trivy 有什么区别？

CodeQL 主要分析源码语义和数据流，寻找代码层漏洞模式；Trivy 主要检查依赖与镜像 CVE、文件系统秘密和 IaC 配置。两者覆盖面不同，需要结合人工审查。

扫描发现 HIGH 漏洞就一定阻止发布吗？

应结合是否可修复、是否实际可达、运行权限和补偿控制判断，但必须有明确策略、owner 和到期日。金融核心通常对可利用高危问题采用 fail-closed。

公开代码如何避免泄密？

只放合成数据和参考配置；使用秘密扫描、最小化示例、环境变量占位、提交前检查和历史清理流程。公开仓库不应包含真实客户、密钥、内网地址或受限文档。

08 / 不要这样说

四个常见工程包装误区。

!

“CI 绿了，所以没有 Bug”

CI 只证明已定义门禁通过，未知风险和缺失用例仍需要评审与监控。

!

“覆盖率 100% 就质量高”

覆盖率不衡量断言价值，关键是风险场景、不变量和失败分支。

!

“安全工具没报错就是安全”

扫描会漏报和误报，还需要威胁建模、人工评审、运行时控制与响应流程。

!

“有在线页面就是生产经验”

演示证明可运行，不等于真实容量、客户数据、合规与运营责任。
